### 1. Source vs. Output Directory Architecture

Keep authored Markdown files separate from compiled build outputs so raw source files do not accidentally ship to production unless intentionally exposed, and group compiled HTML fragments under a single URL prefix for uniform HTTP headers and Service Worker caching.

| Source Path (Authored) | Compiled Output Path (Served) | Notes |
| --- | --- | --- |
| `./public/datasets/{id}/datasheet.md` | `./public/datasets/{id}/datasheet.html` | Co-located with `data.csv` and `metadata.json` so each dataset folder remains self-contained.

 |
| `./content/models/*.md` | `./public/fragments/models/*.html` | Compiles model cards (e.g., `card.md` or per-algorithm cards) into fetchable partials. |
| `./content/pages/*.md` | `./public/fragments/pages/*.html` | Compiles informational pages (About, Privacy, Methodology) displayed in dialogs. |
| `./content/help/*.md` | `./public/fragments/help/*.html` | Compiles contextual metric, parameter, and UI help tooltips/modals. |
| *(Generated at build time)* | `./public/fragments/manifest.json` | Maps logical IDs (e.g., `"help/roc-auc"`) to titles, URLs, and content hashes. |

Treat `./public/fragments/` (and compiled `datasheet.html` files) as **gitignored build artifacts** generated by `bun run build:content` before bundling the app.

### 2. Emit HTML Fragments, Not Full HTML Documents

Because your web app fetches these files via `fetch()` and injects them into a `<dialog>` element, the build script must output **HTML fragments** (inner markup only: `<h2>...</h2><p>...</p>`), **not** full `<!DOCTYPE html><html><head>...` documents.

* **Valid DOM & Styling:** Injecting a full `<html>` document inside a `<dialog>` creates invalid nested document roots and forces the browser to strip or misplace `<head>` tags. Fragments inherit your application's typography, CSS custom properties, and dark/light theme automatically.
* **Preserve In-App State:** Configure the Markdown renderer to add `target="_blank" rel="noopener noreferrer"` to all external `http(s)://` links. If a user clicks an academic citation inside a `<dialog>` while configuring a model, it opens in a new tab instead of navigating away and wiping their in-memory Web Worker state.
* **Deterministic Heading IDs:** Enable heading slug generation (e.g., `marked-gfm-heading-id`) so `<dialog>` components can jump directly to sub-sections (such as `#ethical-considerations` inside a dataset card).

### 3. Preventing Standalone Crawler Indexing (`X-Robots-Tag`)

When HTML files are fragments without a `<head>` element, you cannot rely on `<meta name="robots" content="noindex">`. Instead, enforce non-indexability at the **HTTP header** and **DOM trigger** layers:

1. **Serve `X-Robots-Tag: noindex, nofollow` Headers (Primary Control):**
Configure your static host (e.g., `public/_headers` on Cloudflare Pages/Netlify, or Nginx/Caddy rules) to attach `X-Robots-Tag` to every fragment path:
```text
/fragments/*
  X-Robots-Tag: noindex, nofollow

/datasets/*/datasheet.html
  X-Robots-Tag: noindex, nofollow

```


Search engines (Googlebot, Bingbot) honor `X-Robots-Tag` on any HTTP response identically to a `<meta name="robots">` tag, ensuring raw unstyled fragments never appear in search results.
2. **Do NOT Block `/fragments/*` in `robots.txt`:**
A common mistake is adding `Disallow: /fragments/` to `robots.txt`. If an external site ever links to a fragment URL, `Disallow` prevents crawlers from fetching the response to see the `X-Robots-Tag: noindex` header—causing the URL itself to still be indexed without a snippet. Leave `/fragments/` crawlable so bots read `X-Robots-Tag: noindex` and drop the URL.
3. **Trigger Dialogs via `<button>` Elements, Not `<a href>` Links:**
In your UI components, trigger help dialogs using `<button type="button" data-doc="help/roc-auc">` + `fetch()` rather than `<a href="/fragments/help/roc-auc.html">`. Crawlers do not follow `data-*` attributes on buttons, preventing bots from discovering fragment URLs in the first place while ensuring the content is only indexed if rendered inline as part of a host application route.

### 4. Build Script & Content Pipeline Best Practices (`Bun`)

When specifying the `bun` build script for your coding agent, enforce four pipeline safeguards:

* **Strip YAML Frontmatter Before Rendering:**
Files like `datasheet.md` use YAML frontmatter (`--- ... ---`) for structured metadata. The build script must parse and strip frontmatter first (storing fields like `title` or `pretty_name` in `manifest.json`) before passing the Markdown body to the HTML compiler; otherwise, frontmatter renders as horizontal rules and raw key-value text inside the `<dialog>`.
* **Build-Time Link & Asset Validation:**
Have the Bun script scan compiled HTML for relative links (`./...`, `/...`) and `<img>` sources, failing the build if any referenced target does not exist in `./public/`. That prevents broken links inside modal dialogs.
* **Incremental / Watch Mode Support:**
Support both a one-shot CI build (`bun run build:content`) and a `--watch` flag (`fs.watch` on `./content` and `./public/datasets/**/datasheet.md`) so editing a help `.md` file updates the `<dialog>` immediately on refresh during local development.
* **Deterministic Output & Cache Busting:**
Include a short SHA-256 content hash per entry in `/public/fragments/manifest.json` so your client-side dialog loader can append `?v=<hash>` (or invalidate its in-memory `Map` cache) whenever a Markdown file changes across deployments.
