# Machine Learning Orchestrator

**Status:** implemented — local single-target classification with One-Shot and fixed-parameter Cross-Validation, with saved evaluation outputs for numbered results.

## 1. Runtime boundary

Samatā owns the model builder, input transport, training coordination and durable results. The `web-ml` package owns stratification, fitted preprocessing, model fitting, evaluation, cross-validation and diagnostics. Bun installs the versioned release tarball from `vendor/web-ml/`. The build verifies the installed release and serves its module graph, relative workers, WASM files and notices from a versioned, content-addressed same-origin directory. New training results record the release tarball's SHA-256 in `webMlRevision`. See [Delivery and Caching](ARCHITECTURE.md#delivery-and-caching) for isolation and installation.

The app starts one module worker at `/training.worker.js` per accepted attempt. The worker imports the verified runtime and uses the package's own worker and WASM graph. A non-isolated page stays in Training Setup with a recovery message. The browser owns the WebAssembly and shared-memory resources used by the library.

## 2. Input and evaluation

The worker reads the acknowledged dataset by ID. It reads bounded IndexedDB pages, verifies column metadata and row types, and preserves the mapping from dense accepted rows to original row indices. Rows with missing or invalid target values are excluded and counted. The worker preserves missing predictor values for the library. The transport encodes each selected feature and class without fitting statistics.

- **One-Shot.** The app calls `holdoutValidate` once with a 20% test ratio, seed 42 and `returnFit: true`. The library stratifies the split, fits preprocessing on the fitting rows, transforms the held-out rows with that state and returns the fitted model and fitted preprocessor from the same fit. There is no second training attempt.
- **Cross-Validation.** The app sends the selected fold count, seed 42, fixed manual options, accuracy scoring and `refit: true` to `crossValidate`. The library fits preprocessing and the model inside each fold, scores its validation rows and refits on all eligible rows. The stored folds and out-of-fold diagnostics describe the evaluation. The stored model and fitted preprocessor describe the separate full-data refit.
- **Evaluation outputs.** Both calls also request `evaluation: { outputs: true, reports: true, trainingReports: true, baselines: ['most-frequent', 'stratified'] }`. Binary targets name the second class of the request axis as the explicit positive label. The library returns per-row outputs, a held-out report and a training report for each partition, and both baseline reports for each partition (WR-1…WR-6). The worker then calls the public curve functions on the pooled held-out rows: `rocCurve` and `precisionRecallCurve` for binary ranking, `oneVsRestCurves` for multiclass, `binaryThresholdSweep` over 101 cutoffs and `calibrationCurve` with ten uniform bins (WR-10). Samatā computes no metric, curve, baseline or partition.

### Stored evaluation

The worker maps these outputs into `StoredEvaluation` (`src/types/model-evaluation.ts`, version 1), which belongs to Samatā so that later library changes cannot silently break saved results. Before mapping, the worker confirms that the library's declared class axis equals the request axis element for element, including label types; a mismatch is a contract error and the returned model is still disposed once. It holds the class axis, the explicit positive class index for binary targets, the partition fingerprint, one entry per partition (held-out report, training report, both baselines, duration and timing kind), the pooled held-out report and baselines, the per-row outputs and the curves. One-Shot is one partition of kind `holdout-test`; Cross-Validation is one `outer-fold` partition per fold. Source row indices are mapped back to original dataset rows. Metrics keep the library's value or its unavailability reason. The partition fingerprint is a SHA-256 over the dataset ID, protocol, seed, class axis and the sorted pairs of original row and partition, so matching held-out rows can be recognised across models. `decodeStoredEvaluation` validates every stored evaluation on read.

The eight classifier adapters pass the active validated option overrides. Step 4 checks observed class counts and the user's fold count. The library decides whether its split and estimator can execute. A safe rejection for the displayed local run enters Training Stopped with the applicable reason and an Edit Training Setup action.

## 3. Worker messages and progress

`TrainingStartRequest` captures the dataset, target, model number, creation timestamp, configuration key and run ID together with the classifier, features and setup. Each worker processes a single start. Cancellation addresses that worker's run ID and aborts the library through its signal. Main-thread decoding checks the captured identity and payload before applying any message. Late progress, mismatched attempts and duplicate terminal replies cannot settle the run.

The configuration key excludes the library-owned KNN `leafSize` and MLP `validationFraction` defaults added to the 0.2.0 catalogue. This preserves the keys used to restore earlier saved results.

The worker returns progress with optional structured log entries, a result payload, a safe error code or cancellation. The session stores a compact progress snapshot and at most 250 ordered entries. An indeterminate native bar omits its value. The app retains the last measured fraction during saving and reserves 100% for acknowledged success. After a matching local stop, the same run's last measured percentage and log stay visible until retry, edit or departure. The entry keys let the builder localise milestone announcements without exposing raw errors. See [Training Progress](components/training-progress.md).

## 4. Publication and recovery

Training holds a shared ingestion lock and an exclusive per-model lock. Start, success, cancellation and failure use the acknowledged training-domain journal. Start publishes the exact identity and setup before creating the worker. On success, the service commits a checked version 2 result and the matching pending state together in IndexedDB, with headline metrics projected from the stored evaluation. A first provisional finish pins the exact run and clears the pointer in that commit. The same guarded finish assigns the app swatch and mirrors the optional saved label. The envelope keeps the model and preprocessor JSON, web-ml revision, source row indices, labels, duration, final log and evaluation with the strategy's partitions. Version 1 results stay readable and display a legacy message for unavailable details.

A saved result awaiting publication retains its run ID and the last measured progress. Retry and startup replay publish the same committed operation. Recovery after a failed start publication returns to the saved draft if no worker owns it. An explicit retry from Training Stopped starts a distinct attempt. Confirmed departure cancels or waits for a matching local run and rechecks the acknowledged provisional identity before discarding. If finish wins the race, departure preserves the trained result.

**View Results** on the provisional visit verifies and acknowledges the pinned first run, then replaces the visit with its numbered results route. That route reads the evaluation with full run identity through `$modelResults`, including for direct links. [Application State Persistence](state-and-storage.md#6-indexeddb-reconciliation) defines the locks, journal and restoration order. Tuned execution and model-specific results are follow-up phases.

## 5. Paired comparison analysis

The separate same-origin module `/analysis.worker.js` loads the same pinned runtime and invokes the public `bayesianCorrelatedTTest(scoresA, scoresB, { rope, testFraction })` for equally sized, finite held-out balanced-accuracy fold arrays. `testFraction` is `1 / k` for `k` paired folds. The request is `{ id, type: 'rope', scoresA, scoresB, rope, testFraction }`; replies are `{ id, type: 'rope-result', result }` with lower, equivalent and higher probabilities, or `{ id, type: 'rope-error', reason }` with `invalid-input` or `analysis-failed`. Guards validate request IDs, arrays, bounds and probability sums. The client debounces width edits by 250ms, cancels superseded requests, ignores stale responses, retries with a fresh worker after failure and disposes it when the route is left. One-Shot results do not request a posterior. The app does not compute the posterior itself.
