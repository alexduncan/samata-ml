## Goal

**Current behaviour:** `src/features/models/app-model-builder-view.ts` (L1092–1098) renders Section 4 (`4. Training Setup`) via `renderPendingSection` (L1008–1031) as `<p class="pending-notice">Not available yet.</p>`. `src/types/state.ts` (L80–83) defines provisional `ValidationMethodology` variants (`nested_cv`, `k_fold_cv`, `train_test_split`), and `src/stores/persister.ts` (L92, L257–267) checks only `trainingSetup.type` without validating numeric fields. `src/features/models/app-models-view.ts` (L285–287) renders the raw `model.trainingSetup.type` string. Reserved routes (`src/types/routes.ts` L5, `src/router/route-parser.ts` L36–38) hard-code individual help paths rather than supporting dynamic `/help/*` pages compiled from `content/{locale}/pages/*.md`.

**Target behaviour:** Section 4 lets a user configure One-Shot (a requested stratified 80% / 20% holdout, seed 42) or Cross-Validation (a single fold count, seed 42). The default is One-Shot. The fold controls show up to ten folds and a labelled partition diagram. Choices require current target statistics. **Train Model** saves the valid setup, completes Section 4, displays its summary with **Edit**, and opens the pending Section 5. The model stays a draft. Reload and rollback between the two compatible v1 readers preserve the active dataset. Both the builder and the models list show the same summary, and the form links to `/help/training-setup`.

**Why:** Give users a reproducible evaluation configuration they can inspect before training. Manual CV and future tuning share the selected outer-fold count. Phase 3 owns execution through the public library.

### Interfaces and behaviour

#### A. State, constants, and pure domain helpers

```ts
// src/types/state.ts
export const FIXED_ONE_SHOT_TEST_RATIO = 0.2 as const;
export const FIXED_TRAINING_RANDOM_STATE = 42 as const;
export const MIN_CV_FOLDS = 2;
export const MAX_CV_FOLDS = 10;
export const DEFAULT_CV_FOLDS = 5;

export type ValidationMethodology =
	| {
			type: 'one_shot';
			testRatio: typeof FIXED_ONE_SHOT_TEST_RATIO;
			randomState: typeof FIXED_TRAINING_RANDOM_STATE;
	  }
	| {
			type: 'nested_cv';
			outerFolds: number;
			innerFolds: number;
			randomState: typeof FIXED_TRAINING_RANDOM_STATE;
	  };

export const DEFAULT_ONE_SHOT_SETUP: ValidationMethodology = {
	type: 'one_shot',
	testRatio: FIXED_ONE_SHOT_TEST_RATIO,
	randomState: FIXED_TRAINING_RANDOM_STATE
};
```

**V1 storage boundary.** The application types above describe store values. The old reader accepts three wire tags and ignores the additional seed field (`persister.ts:92,257–267`). Use a private encoder/decoder within the persister. All existing unrelated envelope validation, version checks, storage keys and read-only mode still apply.

| Application value | Value written at `models[i].trainingSetup`                             |
| ----------------- | ---------------------------------------------------------------------- |
| `null`            | `null`                                                                 |
| `one_shot`        | `{ type: 'train_test_split', testRatio: 0.2, randomState: 42 }`        |
| `nested_cv`       | `{ type: 'nested_cv', outerFolds: k, innerFolds: k, randomState: 42 }` |

- Encode at both `writeAppStateNow` and `persistNow` (`persister.ts:482,519`). This covers debounced, synchronous, explicit, page-hide and startup writes. Serialisation leaves the store’s objects intact. Phase 1’s hyperparameter normalisation and the existing scroll schema still apply.
- On read, accept `null`; map `train_test_split` at exactly 0.2 to One-Shot, `k_fold_cv` with an integer `folds` in 2…10 to equal inner/outer counts, and `nested_cv` with equal integers in 2…10 to the same pair. For these legacy tags, a missing own `randomState` takes the fixed default 42. A supplied seed must equal 42. Only construct fresh objects from validated own fields. A non-object, unsafe own prototype key, missing required numeric field, unequal counts, custom ratio or seed, unknown tag, fractional or non-finite count is an unusable setup. Do not coerce malformed values or silently choose different folds.
- During decode distinguish a valid setup, an explicitly stored `null`, and an unusable or absent field. Keep that distinction until the owning model has been checked. An **original draft** needs setup repair only for an unusable field or for explicit `null` with a `configure-training`, `training` or `results` completion. In that case set the setup to `null`, remove those completions and clear stale progress, timings, duration, metrics and error. Retain any existing `TRAINING_INTERRUPTED_BY_RELOAD` diagnostic, Sections 1–3, their values and model UI state.
