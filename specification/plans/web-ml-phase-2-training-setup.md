## Goal

**Current behaviour:** `src/features/models/app-model-builder-view.ts` renders Section 4 (`4. Training Setup`) through `renderPendingSection` (L1222–1245) at L1301–1307 as `<p class="pending-notice">Not available yet.</p>`. `src/types/state.ts` (L80–83) defines provisional `ValidationMethodology` variants (`nested_cv`, `k_fold_cv`, `train_test_split`). `src/stores/persister.ts` (L92, L275–285) checks only `trainingSetup.type`. `src/features/models/app-models-view.ts` (L284–287) renders the raw `model.trainingSetup.type` string. The reserved Help routes are a closed list of fixed paths (`src/types/routes.ts` L5, `src/router/route-parser.ts` L35–43); Phase 1 added `/help/configure-model` this way.

**Target behaviour:** Section 4 lets a user configure One-Shot (a requested stratified 80% / 20% holdout, seed 42) or Cross-Validation (a single fold count, seed 42). The default is One-Shot. The fold controls show up to ten folds and a labelled partition diagram. The fold range is limited by the current target's class counts, a recorded samatā UI rule (D7). **Train Model** saves the valid setup, completes Section 4, displays its summary with **Edit**, and opens the pending Section 5. The model stays a draft. Reload and rollback between the two compatible v1 readers preserve the active dataset. Both the builder and the models list show the same summary, and the form links to the new fixed Help page `/help/training-setup`.

**Why:** Give users a reproducible evaluation configuration they can inspect before training. Manual CV and future tuning share the selected outer-fold count. Phase 3 owns execution through the public library.

**V1 storage boundary.** The types above describe store values. The previous reader accepts three wire tags and ignores extra fields (`persister.ts:92,275–285`). Use a private encoder/decoder within the persister. All other envelope validation, version checks, storage keys and read-only mode still apply.

| Application value | Value written at `models[i].trainingSetup`                             |
| ----------------- | ---------------------------------------------------------------------- |
| `null`            | `null`                                                                 |
| `one_shot`        | `{ type: 'train_test_split', testRatio: 0.2, randomState: 42 }`        |
| `nested_cv`       | `{ type: 'nested_cv', outerFolds: k, innerFolds: k, randomState: 42 }` |

- Encode at both `writeAppStateNow` (L488) and `persistNow` (L522). This covers debounced, synchronous, explicit, page-hide and startup writes. Serialisation leaves store objects intact. Phase 1's hyperparameter normalisation and the scroll schema still apply.
- On read, accept `null`; map `train_test_split` at exactly 0.2 to One-Shot, `k_fold_cv` with an integer `folds` in 2…10 to equal inner/outer counts, and `nested_cv` with equal integers in 2…10 to the same pair. A missing own `randomState` takes 42; a supplied seed must equal 42. Construct fresh objects from validated own fields only. A non-object, unsafe own prototype key (`__proto__`, `constructor`, `prototype`), missing numeric field, unequal counts, custom ratio or seed, unknown tag, or fractional or non-finite count is an **unusable setup**. Never coerce or choose different folds.
- Preserve decode outcomes from the persisted reader to the reconciler. Add a transient `trainingSetupDecodeOutcomes: readonly ('valid' | 'explicit-null' | 'unusable')[]` to the valid result of `validateAppState` and forward it in `PersistedRead` alongside `state` and `scroll`. Align each outcome to the original `state.models[i]` by index. Both explicit `null` and unusable setup decode to `null`. Use an empty array on default-state reads. The reconciler checks the original status, outcome and completions before catalogue, feature and lock repair can remove steps, then applies setup recovery after result and lock checks. Earlier branches that clear the model list discard the outcomes. Keep the array out of the application store and all wire payloads. `reconcileStartupState` is the only reader.
- An **original draft** needs repair only when its outcome is `'unusable'` or it is `'explicit-null'` and the model has a `configure-training`, `training` or `results` completion. Repair sets the setup to `null`, removes those completions and clears stale progress, timings, duration, metrics and error, except an existing `TRAINING_INTERRUPTED_BY_RELOAD` diagnostic. Sections 1–3, their values and model UI state are retained. A draft stored with `null` and no downstream completions round-trips unchanged.
- An **original trained or training model** keeps its status through the existing result and lock checks. A trained model with a verified result keeps its result, status and read-only "Not configured" display when the setup is unusable. A running model owned by another tab stays running. If reconciliation demotes the model to draft (missing result → `TRAINING_FAILED`, `reconciler.ts:215–236`; absent lock → `TRAINING_INTERRUPTED_BY_RELOAD`, L311–328), apply the same repair condition to the original setup and completions. If repair is needed, remove stale Section 4–6 completions and training fields but keep the newly assigned error (code, message, timestamp). Decide precedence from the original state and the transition, never from message text. Later hydration of the repaired draft preserves that error.
- `reconcileStartupState` reads state before orphan cleanup and persists at L333. Setup recovery must keep the original active dataset ID throughout, and keep sibling models and results, dataset metadata, raw rows, scroll, counters, target and resume path. Genuinely orphaned datasets are still removed. A second hydration of the rewritten state is idempotent.

**Eligibility and summaries.** Framework-free `src/features/models/training-setup.ts`; document every export.

- `computeTrainingSetupBounds(targetStats: ColumnStats | null): TrainingSetupBounds`, with `TrainingSetupBounds = { readonly maxFolds: number; readonly minClassCount: number | null; readonly blocked: boolean }`. Its TSDoc states D7: a UI input rule that web-ml may still reject. `null` stats → `{ maxFolds: 0, minClassCount: null, blocked: true }`. Categorical targets use `categoryCounts`; boolean targets use `trueCount`/`falseCount`. Ignore zero-count classes. Iterate once without spreading the map into `Math.min`. Negative, non-finite or fractional counts, a non-record `categoryCounts`, or an unsupported column type → `minClassCount: null`, `maxFolds: 0`, `blocked: true`. Fewer than two observed classes → `minClassCount: 0`, blocked; a smallest class of one → `minClassCount: 1`, blocked. Otherwise `minClassCount = m`, `maxFolds = min(10, m)`, `blocked: false`.
- The two-row minimum also gates One-Shot. Exact 80/20 feasibility and partitioning belong upstream. For later equal-count nested CV the outer training partition must also satisfy `m − ceil(m / k) >= k` (for `m = 4, k = 4` manual CV is allowed but each outer training fold has three minority rows). Phase 7 revalidates. Phase 2 never assigns rows or simulates folds.
- `validateFoldCount(folds: number, maxFolds: number): FoldValidationError | null`, where `FoldValidationError = 'invalid-number' | 'out-of-range'`: non-finite → `'invalid-number'`; non-integer or outside `2…maxFolds` → `'out-of-range'`.
- `createCrossValidationSetup(folds: number): ValidationMethodology` returns `{ type: 'nested_cv', outerFolds: folds, innerFolds: folds, randomState: 42 }`; callers validate first.
- `formatTrainingSetupSummary(setup: ValidationMethodology, labels: TrainingSetupSummaryLabels): string`, with `TrainingSetupSummaryLabels = { readonly oneShot: string; readonly crossValidation: (folds: number) => string }`. English: "One-Shot (80% / 20%)" and "Cross-Validation (5 folds)". Incomplete records and recovered records without a usable setup show "Not configured" in the list.
