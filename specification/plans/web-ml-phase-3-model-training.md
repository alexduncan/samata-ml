## Goal

**Current behaviour:** Valid Training Setup submission saves the setup and opens the Section 5 placeholder while the model stays a draft. The store has lifecycle actions and IndexedDB reserves a result store, but there is no training service, result writer or deployed web-ml runtime.

**Target behaviour:** **Train Model** starts local, manually configured classification in a worker. One-Shot evaluates a stratified 80/20 holdout. Cross-Validation evaluates fixed options across the chosen number of stratified folds and refits once on all eligible rows. Section 5 displays a single native progress bar, a disclosure with a chronological status log, cancellation and elapsed time on success. Successful runs store their result before publishing trained status. **View Results** acknowledges success and opens the existing Section 6 placeholder.

**Why:** Learners can run and retry a real, reproducible evaluation protocol without blocking the interface or uploading their data. Later phases can consume durable trained artefacts.

## Scope

**In scope**

- Deploy the matching prebuilt web-ml module, worker and WASM assets. Enable cross-origin isolation in development and verify the existing production headers.
- Support the eight Phase 1 classifiers for categorical or boolean targets. Use the existing option policy, feature selection and Phase 2 training setup.
- Read typed raw rows, exclude missing target rows, invoke web-ml APIs, store a versioned result and drive accessible progress and retry.
- Coordinate cancellation, reload, target changes and dataset replacement across tabs.

**Out of scope**

- Regression, hyperparameter tuning including nested CV, live or post-training timing breakdown tables, Section 6 results rendering, comparison, advanced reports and row-level outputs. See [Phases 4–7 and the WR ledger](web-ml-classification-integration.md#scope).
- Visual promotion of the Section 5 draft, a general cross-tab synchronisation redesign, and service-worker installation.

**Constraints and invariants**

- web-ml owns partition selection, preprocessing fit and transform, estimator fitting/refit and every reported metric. Samatā handles reading and packaging rows, dispatch, persistence and display.
- Dataset rows, class labels, predictions, fitted artefacts and logs stay in the browser. A fitted k-neighbours snapshot can contain training rows, so it shares the dataset deletion lifecycle.
- Strict TypeScript, TSDoc, WCAG 2.2 AA, British English, project i18n and the existing token vocabulary. Keep the training service and worker free of Lit. Worker code never imports app stores.
- Keep the existing database stores and real result key `[datasetId, modelNum]`, and the v1 Training Setup wire format. Add a tagged coordination record in the existing result store, without a database version bump. Read earlier drafts and progress objects. Pin the runtime and typings to one matching web-ml build.

Tuning requires a later workflow. Refit adds one fit and supplies the model artefact for Phase 6.              |
| D2 — Raw transport       | Build one transport dictionary with `encodeTabularFeatures` and hand the schema to both train and evaluation. Request per-partition preprocessing with `standardize: false`.                                     | A globally fitted dataset transform leaks validation information. Transport dictionary codes carry nominal identity only.                                        |
| D3 — Deployment          | Serve matching, same-origin prebuilt JS and WASM under a deterministic versioned URL, preserving their relative graph. Compile that URL into the integration worker.                                             | Rebundling web-ml can rewrite its worker/WASM paths. | D4 — Commit point        | Keep training cancellable until saving starts. Hold the data and model locks through the result commit and state publication. Recover post-commit crashes from a matching envelope.                              | Clearing locks before the commit admits a concurrent discard. Marking trained before the transaction completes can leave a broken model.                         |
| D5 — Display             | One native progress bar and one recoverable disclosure. | D6 — Feasibility         | Keep Phase 2's class-count UI limits. | D7 — Durable publication | Atomically record the protected domain candidate and generation with its IDB resource mutation, acknowledge localStorage, then publish memory. ### Interfaces and behaviour

#### Dataset and upstream requests

- Capture an immutable request identity from the submit snapshot: dataset ID, target name, model number, model creation timestamp, and a canonical key for algorithm, ordered features, effective options and setup. Allocate a fresh run ID (`crypto.randomUUID()`) for the attempt. Keep the Phase 1 normaliser's active request options and reject a failed normalisation at launch. Keep fixed/hidden options omitted under the established policy. Use the algorithm discriminator and an exhaustive typed adapter for the eight catalogue IDs. Launch only with manual options, an eligible target, completed prerequisite sections and at least one selected feature.
- In the worker resolve selected columns against current dataset metadata and page `raw_records` in offset order using `getRows`. Preserve feature order, source row indices and class/row association. Exclude and count only null targets. Construct a single stable label axis by first occurrence among retained rows and write one contiguous Float64 code per retained row. Preserve boolean labels in that axis. Accept numeric, categorical and boolean features under the existing eligibility rules. Transport numeric values as numbers, categorical values verbatim and booleans as categorical strings `true` and `false`. Preserve nulls. Reject any metadata or row-type mismatch before fitting. Check abort between page reads and before starting the library run.
- Use `encodeTabularFeatures(rows, columns)` once. The index-backed `PartitionDatasetProvider` implements the public `DatasetProvider.load(features, targets?, signal?, onProgress?)` and exposes caller-allocated row-major values at the supplied indices in their supplied order. Both partitions use the same transport schema. Missing values remain available to the library as missing data. Check buffer dimensions and cancellation, and keep progress monotonic within each load. Keep retained input indices available until the run completes so a returned partition index can be traced to a source row.
- For One-Shot call `stratifiedTrainTestSplit(codes, { testRatio: 0.2, randomState: 42 })`. Call `createTrainingClient().train` with the indexed train provider as `data`, `validation: { data: testProvider }`, `classLabels`, the validated classifier options and `preprocessing: { columns, standardize: false }`. Require a held-out single-target classification report from `await run.result` and save it with the split indices. Preserve probability-metric availability tags. A missing report on a successful validated run is a contract error.
- For CV call `crossValidate` with the full prepared provider, `folds: trainingSetup.outerFolds`, `randomState: 42`, `scoring: 'accuracy'`, `classLabels`, the validated options, the same preprocessing policy and `refit: true`. Leave `includeMetrics` unset and retain the always-present classification diagnostics. Save the returned fold scores/indices, pooled diagnostics, mean score and dispersion. The refit artefact is trained on all retained rows and supplies the stored fitted model and transformer through `result.refit`. A missing requested refit or missing fitted transformer is a contract error. It does not add to the out-of-sample report.
- Send options and identifiers only in the main-to-worker request. The dedicated app worker owns row reads and the web-ml run. It copies upstream model JSON and fitted transformer JSON before disposing any disposable fitted estimator. Preserve each explicit report or estimator label axis in its own order. Do not enable SVC probabilities implicitly, replace unsupported data with made-up values or implement a fallback estimator.

#### Protocol, progress and result

- `training/protocol.ts` defines structured-cloneable messages. Main sends `start` with the run identity/request or `cancel` with the run ID. Worker sends `progress`, `success`, `failed` or `cancelled`, each with the run ID. One worker handles one attempt. Validate kind, payload and run identity before applying messages. Only the first terminal message settles, and worker `error`/`messageerror` also settle. Ignore late messages from an older attempt or mismatched dataset, target or model.
- Store compact `TrainingProgress` as `{ percent: number | null, stage: TrainingStage, phase: string | null, statusMessage: string }`. App stages are `preparing | fitting | cross-validation | refitting | evaluating | saving`. Consume each run’s `events` while awaiting `result`. Normalise training `phase`, `progress.fraction` and warning events. CV uses `fold-start`, `fold-progress`, `fold-complete`, `refit-start`, `refit-progress` and `refit-complete`. Follow the number of distinct completed folds for overall progress because the public contract does not specify a base for `foldIndex`. Terminal events and the result promise settle through the same guard. Use an indeterminate bar until a reliable run-level measure is available. One-Shot maps reported fit fractions to 10–85%. CV maps completed folds to 10–85% and never advances from a repeated or lower count. Hold the last determinate value during evaluation/refit. Saving displays 95%. Reserve 100% and View Results for both committed IDB success and acknowledged state publication. An IDB success awaiting publication stays at 95% with a saved-result recovery notice. Initialise from zero or indeterminate on each new attempt.
- The session store is keyed by dataset/model/run identity and holds the latest progress plus up to 250 chronological `TrainingLogEntry` items with stable monotonically increasing IDs, timestamps, level and localisable message data. Append phase/fold boundaries, deduplicated warning codes and terminal events. Coalesce repeated ticks; retain the newest 250 when over the cap. Append the success item to the candidate envelope before saving and publish it in the live session only after commit and state acknowledgement. Persist compact ticks at the existing one-second throttle; entry/exit use acknowledged protected commits and disclosure toggles request an immediate best-effort flush. Cancelled or failed attempts present the terminal notice in Section 4.
- Define `ResultEnvelope` in `src/types/model-result.ts` with `schemaVersion: 1`, `datasetId`, `target`, `modelNum`, `modelCreatedAt`, `configurationKey`, `runId`, `algorithm`, `webMlRevision`, `durationMs`, `excludedTargetRows`, `featureNamesOut`, `classLabels`, `modelJson`, `preprocessorJson` and `logEntries`. Discriminate `strategy: 'one_shot'` with `holdout: { trainIndices, testIndices, report }` from `strategy: 'cross_validation'` with `crossValidation: { folds, diagnostics, meanScore, standardDeviation }`. Indices are relative to the retained rows and the envelope also stores their source-index mapping. Persist copied structured-cloneable values and the public report/transformer types. Timing uses the service's monotonic start-to-save-start interval and is displayed as total elapsed training time. Phase 4 adds its higher-level `evaluation` field independently.
- Read results through the repository. Validate version, identity, strategy, required payload field shapes and safe finite counts/timings. Persist `ModelRecord.resultRevision: string | null` with the current run ID from start through saved success; historic models decode it as null. Clear it on cancellation, failure or lost results. Require an envelope run ID equal to this revision, including when a number is reused after discard. Phase 4 uses the revision to ignore stale result reads. Legacy key-only rows are invalid results. Keep `ModelRecord.metrics` and `timings` empty for Phase 3 and retain `durationMs` for the overview. Expose `model.ui.trainingLogOpen` as a boolean-only preference, default false, updated by an action preserving other keys. Decode old progress into the new shape without discarding the rest of an otherwise valid v1 envelope.

#### Lifecycle, durability and cross-tab invalidation

- The persister remains the sole localStorage writer. Define `PersistenceAck = { ok: true; generation: number } | { ok: false; reason: 'quota' | 'security' | 'read-only' | 'unavailable' | 'conflict' }`. Its protected commit and retry APIs return `Promise<PersistenceAck>`; a caught exception or document-lifetime read-only mode never reports success. Catch `getItem` as well as `setItem` failures. Reuse the quota policy (drop only scroll data and retry once), then return failure without a retry loop. Ordinary form/UI preferences and progress remain best effort: keep memory edits and raise the existing once-per-document non-blocking save notification. Protected lifecycle changes use the acknowledged protocol below rather than the ordinary memory-first subscription path.
- Add a discriminated `TrainingDomainCheckpoint` record at the reserved composite key `['samata-ml:training-domain', 0]` in `model_results`: `{ kind: 'training-domain-checkpoint', schemaVersion: 1, datasetId: 'samata-ml:training-domain', modelNum: 0, generation: number, pending: null | { operationId: string, kind: 'start' | 'finish' | 'cancel' | 'recover' | 'discard' | 'replace', domain: ProtectedDomainSnapshot } }`. Model numbers start at 1; the sentinel dataset ID is reserved and rejected for real datasets. `ProtectedDomainSnapshot` contains the next domain state needed to recover that operation: `dataset`, `target`, `models`, `nextModelNum`, and data selection/mode repairs. It contains no rows, fitted results or logs. This is a deliberately new tagged row contract in an existing store, not a schema/store addition. Every result reader, range scan, dataset deletion and orphan cleanup excludes this record. Invalid/newer checkpoint versions fail closed for protected writes and cleanup, with a recoverable storage notice.
- The framework-free `src/common/storage/training-domain.ts` owns the checkpoint decoder and atomic transaction API. It takes an expected generation, candidate domain and a closed mutation description (no resource change, insert result, delete captured results, delete captured dataset, or publish a replacement after checking its metadata). Read/compare the generation and write the checkpoint within the same transaction, spanning `metadata`, `raw_records` and `model_results` when deletion requires them. Await `tx.done`; expose conflict separately from storage failure. Do not compose the old independently committed deletion helper with a later checkpoint write. Pending cleanup updates only the matching operation ID/generation and cannot clear a newer candidate.
- Add optional v1 wire field `trainingDomainGeneration` (non-negative safe integer; historic absence means zero). It is not the run ID. Under the short exclusive `samata-ml:training-state` lock, read the latest decoded snapshot and durable checkpoint. Before a new protected operation, finish an existing pending publication; otherwise compare the latest snapshot generation with the retained fence and reject stale/unreadable/read-only input. Compute the candidate from that latest snapshot, patch only the captured model/run or confirmed dataset/target, and reject identity conflicts. Commit the candidate checkpoint at the next generation in the same IDB transaction as any result insertion or destructive deletion. On transaction abort, memory and localStorage retain the prior domain and no candidate is published. Await transaction completion, encode/write the candidate localStorage snapshot with that generation, and publish the candidate to memory only after its successful acknowledgement. Preserve current ordinary settings when composing the write; no subscription echo or recursive locking is allowed.
- Generation coverage is explicit. Increment it for `createModel` (including `nextModelNum` allocation), `setTarget` when the target identity changes, combined `confirmDiscardModels`/target confirmation, `loadDatasetSucceeded`, `clearDataset`, accepted training start, every terminal/recovery repair, and `viewResults` acknowledgement. These are protected service commands returning an asynchronous success/failure result; model creation additionally returns the acknowledged model number and navigates only on success. Preserve pure store reducers behind the service; never treat their existing boolean return as a persistence acknowledgement. Do not call the old synchronous identity-mutating actions from views or ingestion publication. Whole-list discard deletes the captured real results with its candidate in one IDB transaction; there is no individual-model discard action in the current app. Model identity uses its creation timestamp as well as number, and replacement resets never weaken the fence.
- `chooseModel`, `setFeatures`, `initialiseFeatureSelection`, `toggleFeature`, `setModelOptions`, `setHyperparameters`, `setMulticlassStrategy`, `setTrainingSetup`, and Section 1–4 `completeSection`/`reopenSection` remain ordinary committed draft edits with existing memory/debounce behaviour, without generation increments. Their writer may merge only the named configuration/setup/completion fields of the same still-draft model creation identity at the same durable generation; it cannot merge dataset/target identity, model lists/counters, lifecycle status, run/result revision, training/results completion, duration or error. Model-local UI preferences (including disclosure), onboarding, data display, resume and scroll keep their ordinary policy only in the current context. Never replace a whole model or whole app snapshot from an old memory copy.
- Before protected start, await a flush acknowledgement for the initiating draft's captured algorithm, ordered features, effective options, multiclass policy, submitted setup and prerequisite completions under the state lock. Compare its canonical configuration key against the freshly stored draft, rejecting an external conflict rather than substituting another configuration. The following start checkpoint captures precisely that acknowledged draft and a fresh run ID. A failed draft flush or a newer generation launches no worker; retain the local draft values and offer retry. A publication retry never flushes unrelated stale drafts over its pending candidate.
- Clear `pending` only after the matching generation has been acknowledged in localStorage. Retain the coordination row and its monotonic generation fence after clearing; dataset/orphan cleanup must never delete it. If the cleanup transaction fails, leave the pending candidate and retry idempotently later. A crash before IDB commit preserves the old domain/resources. A crash after IDB commit, before localStorage acknowledgement or before pending cleanup, replays the committed candidate before rendering domain-dependent UI or orphan cleanup. Replaying an already acknowledged generation only clears pending. A crash after cleanup uses the acknowledged snapshot, checked against the retained fence. A missing localStorage key with no pending candidate may follow existing fresh-state recovery only through a new protected reset generation; a stale tab may never recreate its old domain. A failed IDB or localStorage read is unavailable, never evidence that a dataset/result is absent.
- Pending replay only republishes the candidate whose resource transaction already committed. It takes the state lock alone and never requests resource locks, probes/deletes resources or starts a worker from inside that callback. Subsequent dataset/result validation, interrupted-run repair and orphan cleanup acquire ingestion/model resources first, then state. A generation newer than an arriving storage event causes a fresh guarded read instead of exposing the event payload. If startup replay/read cannot be acknowledged, render the application shell with an accessible storage-recovery notice and Retry saving action; withhold dataset/target/model views and cleanup until recovery succeeds. Existing unrelated navigation remains available; never render the old target or model domain against already changed resources.
- On localStorage failure after IDB commit, retain the pending candidate and its generation. Block further protected mutation until publication is recovered. Keep a route-independent session status for `publication-pending`, release resource locks after transactions settle, and expose an explicit retry that performs only the pending publication. Retry or reload never retrains, deletes an already replaced dataset, or rolls back to resources already deleted. A saved result awaiting publication stays in Section 5 with Cancel and View Results disabled and “The result is saved, but progress could not be saved. Retry saving.” A committed discard awaiting publication keeps its dialog open, explains that the change is saved and finishing is pending, disables duplicate destructive actions and offers the same publication retry. A failed start publication launches no worker. Its pending start is recovered under the lock, then becomes an interrupted draft because no worker owns it; retrying training creates a fresh run. Distinguish these states from fitting failure, cancellation and a pre-commit deletion failure. Future-version read-only state rejects protected operations before their IDB transaction. Ordinary preferences can continue in memory while protected operations are blocked.
- `startModelTraining` owns preparation, launch and finish independently of route. Hold `samata-ml:ingestion` shared then `samata-ml:training:{num}` exclusive, both with `ifAvailable: true`. The state lock is acquired inside resource locks; a state-lock callback never requests a resource lock. Revalidate the persisted dataset/target/model/configuration and IDB metadata under the locks. Keep a synchronous per-model pending guard from first intent. A rejected acquisition or failed protected start leaves the draft recoverable and surfaces an actionable notice. Persist/acknowledge the new run ID and training status through the checkpoint protocol before posting `start`. Distinct models may run concurrently; every candidate merges the latest domain so another model's outcome survives.
- On local Cancel, keep the UI cancelling until terminal settlement. Send cancel to the app worker, abort row loading and the web-ml run through its public cancellation mechanism and await acknowledgement/terminal settlement, allowing the library grace period. Worker error/protocol failure terminates and settles once. Suppress success if cancellation won before saving. Once saving starts, remove Cancel and await the IDB transaction. Success commits the result and success checkpoint together, then acknowledges/publishes `trainingSucceeded`. Cancellation/failure also uses a protected lifecycle checkpoint; an acknowledgement failure remains recoverable rather than silently clearing the run identity. A result transaction failure keeps the previous domain and returns a retryable saving error through protected recovery. Reopen Section 4 only after the draft repair is acknowledged; if storage remains unavailable, keep the unsettled domain read-only with a recovery notice until repair/reload can finish. Cancellation/failure publication uses “Training stopped, but progress could not be saved. Retry saving.”; it never claims a result was saved. Use only safe library reasons, never stacks or row values.
- Hydration first reads the checkpoint and recovers pending publication, then reconciles under the shared ingestion and relevant model lock. A held model lock means another tab is training. With a free lock, a matching committed envelope recovers success; absent/invalid result returns to draft with interruption. A trained model with a missing/mismatched envelope becomes a lost-results draft. Clear stale duration, result metadata and Section 4–6 completions only through an acknowledged repair. Preserve Phase 2 model-local setup repairs. Startup orphan cleanup runs only after readable, validated, acknowledged protected state, under the exclusive ingestion lock with the active pointer rechecked. Skip cleanup on failed reads, future-version read-only mode or pending publication. Storage events never run startup orphan cleanup.
- Target/dataset confirmation cancels and awaits local attempts in the captured dataset. Then acquire ingestion exclusively with `ifAvailable: true`, recheck confirmation identity and block new local starts. A remote shared holder keeps the dialog open with “Training in another tab” and deletes nothing. Target change atomically deletes the active dataset's real results and writes the reset-target/models checkpoint. Change Dataset atomically deletes the captured metadata, rows and real results and writes the empty-dataset checkpoint. A completed save racing confirmed discard is included in that transaction. Pre-commit deletion failure preserves the old selection/models and allows retry; after commit the new checkpoint is authoritative even if localStorage publication fails. Close only after publication acknowledgement. No rollback may restore a deleted identity.
- For ingestion success, reacquire ingestion exclusively (queued for this terminal hand-off) and recheck the pointer captured at start. Commit the replacement checkpoint only when the new metadata exists, acknowledge publication, then clean older datasets. If publication fails, retain both new and old data until recovery. If another mutation won, delete only this request's unpublished dataset. Cleanup failure after a successful replacement leaves recoverable orphan data and never rolls back the new pointer. All deletion RPCs run inside their owning main-thread resource-lock callback. Confirmed discards remain non-waiting, using the existing dataset-busy message for competing ingestion.
- Every scheduled, immediate, flush and startup localStorage writer must acquire the state lock, read the durable fence and latest snapshot, and merge protected fields from the current generation. An older queued write never republishes a stale dataset, target, run, result revision or model list. If pending exists, it may only complete that publication; otherwise an identity mismatch strips stale protected edits and preserves ordinary current-context settings under their existing last-writer-wins policy. Never run an unchecked synchronous domain write from `pagehide`; an uncompleted best-effort preference flush may be lost. Storage events rehydrate protected domain only after matching it to the fence/pending state, without navigation or echo writes; stale events cannot expose a half-published candidate. A stale queued worker start/result must read the latest generation and revalidate its dataset, model creation, configuration and run identity before taking effect. An unrelated model advancing the generation does not invalidate a still-matching live run; merge its result into the latest candidate. A removed/replaced run never survives that revalidation.
