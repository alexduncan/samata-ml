# Mockup catalogue and styling review workflow

**Status:** archived | **Updated:** 2026-11-19T10:40:53Z

## Goal

**Current behaviour:** `package.json` runs `scripts/serve-ui-scaffold.ts` as `serve:scaffold`. Its catalogue and switcher discover only immediate HTML children of `specification/mockups/ui-scaffold/`. Nested drafts can be opened manually, but are absent from navigation; their basename makes the switcher show an unrelated first option. `specification/mockups/basic-html-structure.html` and CSS/resources are absent. The injected fixed widget has independent hard-coded colours, obscures screenshots and contains a mouse-only collapse control. Recursive live reload already exists. Human styling and promotion are described in `visual-design.md` §1.1, but the review-to-app handoff has no practical checklist or per-file audit command.

**Target behaviour:** `bun run serve:mockups` opens a searchable, grouped catalogue of every regular file beneath `specification/mockups/`, with a prominent “Needs styling” view for drafts. Every HTML page has an accurate preview, source access, clean preview and catalogue navigation. The human can edit local CSS with live reload, request structural changes precisely, obtain actionable accessibility evidence, promote a reviewed mockup and commission a bounded app integration task.

**Why:** Make pending design work discoverable and shorten the loop from unstyled semantic HTML to reviewed CSS and an accessible application implementation.

## Scope

**In scope**

- Canonical command/script naming, recursive discovery, safe read-only serving, compatible old links and fresh live reload.
- Native-HTML catalogue and preview controls, full-path identity, draft/reference/resource grouping, source access and clean previews.
- A local, per-file or whole-folder accessibility report using the installed Playwright/axe dependencies.
- A documented human/agent workflow, CSS review and promotion checklist, markup-request template and application integration evidence.

**Out of scope**

- Styling or promoting existing product drafts, repairing all legacy mockups, editing production components or changing training behaviour.
- Browser code editing, filesystem write endpoints, automatic promotion, review databases, screenshots-as-approval, visual diff services or new dependencies.
- Implementing Storybook or adopting the unimplemented workflow-gates process. Existing plans retain their approval rules.

**Constraints and invariants**

- Bun only; default `http://localhost:3333`, existing `PORT`, `--port`, `--host` and `--open` behaviour remains. No automatic browser launch without `--open`.
- Server endpoints only read files. Only the human changes normative mockups. Agents may change structural drafts; a human's work-in-progress CSS must be preserved.
- Baseline Widely available platform features, WCAG 2.2 A/AA, British English. Use native links/forms/buttons; no app menu/tree widget or new framework.
- No new colours, tokens or decorative CSS for this developer interface. Initially use native browser presentation with minimum reflow sizing/wrapping only (TOOL-01 below); awaiting styling is non-blocking.
- Product CSS still uses `css/root.css` tokens without fallbacks and the existing visual-design translation/deviation rules. The catalogue does not certify a file as accessible or approved from its location, size or timestamp.
- Preserve the dirty working tree. Do not commit, push or switch branches. Re-measure baselines before each implementation task; the agent guide's 52-test count is stale.

### Interfaces and behaviour

**File catalogue contract**

- Rename exported types/helpers consistently: `MockupFileInfo`, `getMockupFiles`, `startMockupsServer`; retain routine helpers such as `extractHtmlTitle`, `formatBytes`, `parseCliArgs`. No exported compatibility wrappers are needed: existing consumers are this script's tests only.
- `MockupFileInfo` contains `relativePath`, `title`, `size`, `isEmpty`, `mtime`, `kind: 'html' | 'css' | 'asset'`, `isDraft`, and optional `counterpartPath`. `isDraft` is true under `ui-scaffold/drafts/`; only HTML drafts count towards Needs styling. Pair an HTML draft with a reference only when removing that exact `drafts/` segment finds an existing file; absence is normal. Report counterpart emptiness separately.
- `/` accepts `q` (case-insensitive path/title substring) and `filter=all|needs-styling|html|css|assets|empty`, default all. Unknown filters fall back to all. Preserve form values on results and reload; native GET navigation supplies Back/Forward and shareable URLs without persistent state. Render total and filtered counts, a no-results message with Reset link, and separate headed Needs styling, References and Resources lists. Include full relative path, title/fallback, text category/empty status, size, full modification date/time with timezone, source link and appropriate open link. List every included regular file exactly once, even `.md` review records. A draft with a counterpart has a labelled comparison link.
- Root `/index.html` remains a catalogue alias; real nested index files remain accessible under `/files/`. `/files/` serves regular files in the root only. `/__source/<relative path>` returns original bytes as `text/plain; charset=utf-8` for HTML/CSS/JS/JSON/Markdown/text (with `nosniff`); binary files use their ordinary asset link, never text decoding. Directory and missing-file requests return escaped 404s. No repository-wide source endpoint.
- Legacy `/00_first-load.html`, `/style.css`, `/css/...`, `/drafts/...`, `/ui-scaffold/...` and `/specification/mockups/...` redirect to the corresponding canonical file; prefix matching requires a segment boundary. Preserve query and fragment behaviour where the browser supplies it. Resolve ambiguous unprefixed paths as legacy scaffold paths; root-level mockups use `/files/` links. Relative HTML/CSS imports therefore resolve within the original directory.
- Decode and validate paths once, reject malformed encoding/NUL with 400, reject traversal/backslash tricks and paths outside the root with 403, and refuse symlink files or ancestors. Reuse lexical containment plus filesystem checks. Escape all file metadata in HTML, attributes and error pages; create helper DOM with text/value APIs rather than interpolating filenames into executable scripts. Reserve `/__hmr` for SSE. The only extra root-external resource, if needed for a future styled tool, must be explicitly planned; none is added here.
- Read fresh inventory per catalogue/preview request. Watch the entire mockups root, including nested CSS and add/rename/delete; use one debounced reload. Send `Cache-Control: no-store` for local files. Cleanup watchers/SSE clients on server stop so fixtures do not leak. A deleted file yields a useful 404 with a catalogue link.

**Preview contract**

- Default HTML responses inject a small open-shadow-root review helper in normal document flow at the start of `<main>` when present, otherwise at the start of `<body>` (or the document element). The `<main>` placement keeps controls clear of fixed sidebars in representative drafts without adding layout CSS. It uses native browser styling and identifies the full path and Draft/Reference status; provides Catalogue, Source, Clean preview and counterpart links, a visible label and select of HTML paths, plus an explicit Go button. Selection alone never navigates. Do not mutate mockup controls, headings, links or form behaviour. No helper collapse UI or custom global keyboard shortcuts.
- `?clean=1` returns the original HTML bytes with no injected helper or SSE script. CSS/assets are unchanged. This is the screenshot/audit mode, and `tests/visual-parity.e2e.ts` must request it. Empty HTML remains empty in clean mode; normal preview explains that it is empty and links to its draft counterpart if present.
- Catalogue and preview navigation remain keyboard operable, with meaningful visible names, one catalogue h1, labelled search/selects, native focus indicators and no colour-only statuses. Catalogue works without JavaScript; only live reload needs script. Apply TOOL-01's minimal sizing/wrapping rules to long path text and controls; add no layout grid, decorative rules or style resets. No mockup CSS is loaded into the catalogue/helper, avoiding shell offsets and inherited contrast failures. Tool-only draft controls require no app parity map entries.

**Accessibility report contract**

- T3 introduces `bun run audit:mockups [relative-path ...] [--port 3333]` (new command, available only after T3). It expects `serve:mockups` already running on localhost; no remote hosts. With no paths, discover all non-empty HTML beneath the root. With paths, validate and audit exactly those HTML files. Reject invalid paths/non-HTML/empty explicit targets rather than claiming a pass. URL paths always use the canonical clean preview.
- Use `@playwright/test` Chromium and `@axe-core/playwright`; tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`. No disabled rules or imported drift exclusions. Save a deterministic-path JSON report and escaped human-readable HTML report under ignored `test-results/mockup-a11y/`; overwrite the selected run's reports to prevent stale-success confusion. Include file, URL, run time, browser/viewport (1440×900), axe version, violations, selectors, help links, incomplete results requiring manual review, passes count, skipped empty paths and navigation/runtime failures. List actual browser availability errors actionably.
- Exit 1 for violations or navigation/runtime errors; exit 2 for invalid arguments, no eligible pages or missing server/browser; exit 0 means no automated violations found, with manual review still required. Incomplete results remain visible and unresolved in the human checklist even on exit 0. A bulk run may fail on existing mockups: that is useful evidence, not a reason to suppress contrast or fail the unrelated repository unit suite.
- Static scans cannot exercise training, upload, focus restoration or error announcements. The review record names which headed states were inspected and which interactive states need the consuming app tests. Open native dialogs through the existing page's real controls where available; otherwise mark their contents untested, never automatically unhide everything to manufacture coverage.

### Recommended human and agent workflow

1. **Choose one surface.** Run `bun run serve:mockups`, select Needs styling and open the draft and its counterpart in separate windows. Check the source behaviour plan and headed empty/blocked/loading/error/populated states before designing. Start with one repeated pattern, then reuse it across related states. Keep the app open separately at the same viewport when an implementation exists.
2. **Write and save CSS.** Work in the actual draft HTML and a human-authored sibling stylesheet such as `drafts/<name>.css`, linked after `../style.css`. Use DevTools to experiment, then copy changes back to those files before reload. Keep new rules scoped to an explicit content wrapper; prefer existing tokens, logical properties, native controls and existing shared patterns. Avoid editing the shared scaffold stylesheet for an isolated experiment: its blast radius includes every reference. Do not remove labels, captions, headings or focus treatment to obtain a visual effect. Start at 1440×900, then check narrow/zoomed layouts before polishing. No new token without a plan decision.
3. **Request markup changes early.** Send a concise request in this chat or place it in a review record: file path and section/selector; current problem; desired layout/interaction; proposed wrapper/order/element change; affected states; accessibility implications; screenshot or CSS snippet when useful. Example: “In drafts/03-0_models-overview.html, Models table: add a wrapper around the table for horizontal scrolling, keeping the caption and native table semantics; apply it to populated and loading variants.” An agent may edit structural drafts within an authorised task, preserving human CSS hooks and reporting the changed selectors. Existing behaviour wins; a new interaction/public API or a larger change goes through a plan. Agents do not rewrite normative mockups. Do not use CSS order to conceal a reading/focus-order problem.
4. **Ask for a review with evidence.** Save a review record in `drafts/reviews/<surface>.md` using the template specified below and request CSS/HTML review. The agent inspects the exact diff, token vocabulary, selector scope, cascade/specificity, shared-rule impact, semantics, responsive behaviour and reduced-motion/forced-colours states. Run the per-file audit, review incomplete findings manually and distinguish new defects from inherited shell defects with explicit A11Y/SEM IDs, selectors and owners. Never call the whole page conformant while inherited failures remain. Retest every affected reference when changing shared CSS.
5. **Complete manual checks.** Tab/Shift+Tab, Enter/Space/Escape as appropriate; logical order, no keyboard traps, visible/unobscured focus and dialog return focus. Review headings/landmarks, names/roles/states, labels/errors and table headers with VoiceOver + Safari (or record another actual screen-reader/browser pair). Check 200% text zoom, 320 CSS-pixel reflow or equivalent 400% zoom, WCAG text-spacing overrides, forced colours and reduced motion. Data tables may scroll as a two-dimensional exception; surrounding controls/prose must reflow. Measure text contrast (4.5:1 normal, 3:1 large), necessary non-text boundaries (3:1) and 24×24 CSS-pixel target size or valid spacing/other exceptions. Record results and unavailable checks, not a single accessibility score.
6. **Human promotion.** After reviewing the evidence, the human chooses the final filename, moves the styled HTML into `ui-scaffold/`, moves its CSS into `ui-scaffold/css/`, adjusts links/imports and replaces a placeholder deliberately. Recheck asset paths, related references and the audit after moving. Remove the DRAFT comment only on the human's promotion. A non-empty file in the reference directory is a design reference, not proof of approval or conformance. Remove the associated styling queue item only once the human says that work is complete.
7. **Commission the app port.** Ask the planning skill for a focused integration plan naming the promoted HTML, CSS/selectors, states and consuming app routes/components. The planner maps global document rules to `css/`, reusable shadow-root rules to `src/styles/*.styles.ts`, and local rules to the owning Lit component; class selectors cannot cross Shadow DOM automatically. Review permitted logical-property, semantic, focus and motion translations; preserve A11Y/SEM deviations explicitly. The implementation uses the Lit skills, adds computed-style parity entries for promoted surfaces at 1440×900, runs token tests and stateful app a11y/keyboard/browser checks, and supplies paired screenshots. Mockup CSS is never blindly imported into the app or automatically copied into components. Remove the integration queue item only when the port is verified and its specs are synced.

**Review record template:** source HTML/CSS paths; source behaviour plan/spec; affected sections/selectors and states; intended final destination; CSS summary and shared-pattern impact; requested markup changes and their resolution; automated command/report/time/viewport; manual check table (check, result, evidence, browser/assistive technology); unresolved findings with severity, selector, register ID and owner; promotion decision made by the human; app integration plan and final verification evidence. Use “pending”, “passed”, “failed” and “not tested” honestly. Do not embed an approval button or fabricate a reviewer stamp. An agent may prepare/update evidence in this drafts subtree; only the human records the design acceptance/promotion decision. Keep outstanding decisions or work linked from HUMAN.md.

**Research basis:** [WAI evaluation overview](https://www.w3.org/WAI/test-evaluate/) explains that tools alone cannot establish accessibility. Use the [WCAG 2.2 Recommendation](https://www.w3.org/TR/WCAG22/), [reflow guidance](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum) and [target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum) for review criteria. The specific local workflow above is this plan's design decision, not a W3C-prescribed process.
